Repository layout

Why plain net/http, not chi or gin. Since Go 1.22 the standard ServeMux matches "POST /api/limiters/{pattern}/check" and exposes path values. Adding a router library to do what the standard library already does is weight without benefit. If middleware chaining ever gets hairy, swapping in chi is a one-line change.

Core interface

Every limiter satisfies the same contract. The State method exists purely so the frontend can visualise what is happening inside each algorithm.

// internal/limiter/limiter.go
package limiter

type Decision struct {
    Allowed    bool
    Limit      int64
    Remaining  int64
    ResetAfter time.Duration  // until the quota is whole again
    RetryAfter time.Duration  // until this request would pass (0 when allowed)
}

type Limiter interface {
    AllowN(ctx context.Context, key string, n int64) (Decision, error)
    Name() string
    State(ctx context.Context, key string) (map[string]any, error)
    Reset(ctx context.Context, key string) error
}

var ErrBackendUnavailable = errors.New("limiter: backend unavailable")

Conventions this repo commits to

ConventionReason
Take redis.Scripter, not *redis.ClientScripter is an interface go-redis already exports; it accepts Client, ClusterClient, Ring and Pipeline. Accept interfaces, return structs.
redis.NewScript as a package-level varScript.Run issues EVALSHA and, on a NOSCRIPT reply, reloads and falls back to EVAL by itself. Never hand-manage the SHA.
ctx context.Context first, passed through to RedisCancellation and deadlines reach the socket rather than being dropped at the package boundary.
Plain config structs, not functional optionsThe five limiters have five different config shapes. fixedwindow.Config{Limit, Window} reads better than WithLimit(...). Revisit only past roughly five optional fields.
Wrap with %w, compare with errors.IsRedis failures must stay inspectable by the caller, never swallowed.
No panic inside internal/limiterLibrary code returns errors; the caller decides what is fatal.

Design decisions

The clock lives in Redis

Every script reads the current time from redis.call('TIME') rather than receiving time.Now() from Go.

  • With several application servers, clock skew means each node computes a different window boundary for the same key.
  • TIME returns {seconds, microseconds}, giving microsecond resolution — enough for the token bucket to account for fractional tokens.
  • From Redis 5 onward scripts replicate by effect, so calling TIME inside Lua is legal. Earlier versions rejected it as non-deterministic.

What happens when Redis is down

AllowN returns (Decision{}, ErrBackendUnavailable) and the middleware decides the policy: fail-open (serve the request) or fail-closed (reject it). Expose it as httpx.Config.FailOpen bool, defaulting to true. This is a classic interview question and deserves to be a visible switch rather than a buried assumption.

The five patterns

Numbered in build order, not alphabetically. Fixed Window comes first because it drags the whole scaffold — interface, middleware, headers, Lua helpers, test harness — into existence on the easiest algorithm. The four that follow are then pure algorithm work.

01

Fixed Window Counter

Difficulty

The one that is wrong on purpose — it exists to demonstrate the boundary burst.

Key
rl:fw:{key}:{windowStart} where windowStart = now - (now % windowMs)
Type
String counter
Script
Derive windowStart from TIME → GET → if count + n > limit deny → otherwise INCRBY and PEXPIRE
Config
Limit int64, Window time.Duration

Gotchas

  1. Sliding TTL. Calling PEXPIRE key window on every request keeps the key alive past its own window. The correct expiry is windowStart + window - now, or set the TTL only when INCRBY returns exactly n, meaning the key was just created.
  2. The boundary burst. At 100 requests per minute, 100 requests at 00:59.9 plus 100 at 01:00.1 is 200 requests in 200 milliseconds. Twice the configured limit, entirely within the rules.

Tests

  • limit=5 → five allowed, sixth denied
  • Fast-forward past the window boundary → five allowed again
  • Boundary-burst test. Five at the end of window N, five at the start of N+1, then assert ten requests landed inside less than one window. This test is meant to pass — it documents the flaw.
  • TTL: the key is gone after window elapses
  • Cost greater than one (n > 1)
02

Sliding Window Log

Difficulty

Exact by construction. This becomes the ground truth the other four are measured against.

Key
rl:swl:{key}
Type
Sorted set — score is the millisecond timestamp, member is a unique id
Script
ZREMRANGEBYSCORE key 0 (now-window) → ZCARD → if full, read the oldest entry with ZRANGE key 0 0 WITHSCORES to compute RetryAfter = oldest + window - now → otherwise ZADD and PEXPIRE
Config
Limit int64, Window time.Duration

Gotchas

  1. Members must be unique. Using the timestamp as the member means two requests in the same millisecond collide — ZADD overwrites, the set holds one entry instead of two, the count runs low and traffic leaks past the limit. Build the member as now_micros .. "-" .. INCR(counter) inside Lua, or pass a UUID down from Go. This is the single most common bug in this pattern.
  2. Memory is O(limit) per key. A limit of 10,000 across a million users is an enormous amount of sorted set. Write down in the README why production rarely picks this.
  3. Cost above one needs n separate members added — or a deliberate decision that this limiter only supports n = 1.

Tests

  • Fill to limit, next request denied, advance one window, requests free up individually rather than resetting as a block
  • Two requests inside the same millisecond must both be counted
  • RetryAfter matches the expiry of the oldest logged entry
  • Sliding behaviour: allow 5 at limit 5, advance half a window → denied; advance the other half → 5 allowed
03

Sliding Window Counter

Difficulty

The approximation that ships. Cloudflare runs this one.

Keys
rl:swc:{key}:{windowStart} — two are read: the current window and the previous one
Type
String counters, same shape as Fixed Window
Formula
weight = (window - elapsed) / window
estimate = prevCount * weight + currCount
allow when estimate + n <= limit
Script
GET prev, GET curr, compute the estimate in floating point, compare, then INCRBY curr and PEXPIRE curr (2*window)

Gotchas

  1. It assumes the previous window was evenly spread. If all 100 of the previous window's requests arrived in its first second, the weighting still treats them as uniform. Real traffic lands inside about one percent; adversarial traffic drifts further.
  2. TTL is 2*window, not window. The previous window's counter has to outlive its own window so the current one can read it.
  3. RetryAfter cannot be exact. It has to be approximated by solving for the moment estimate decays below the limit. That imprecision is a genuine property of the algorithm, not a shortcut.
  4. Floats crossing the Lua boundary get truncated (see pattern 04). Return estimate * 1000 as an integer, or a string.

Tests

  • Accuracy test against Sliding Window Log. Generate one traffic sequence — say 200 Poisson-distributed requests over three windows — run it through both limiters, count the decisions that disagree, assert the divergence stays under a threshold such as five percent. This is the most valuable test in the repository.
  • Weight decay: fill the previous window, advance half a window, assert remaining is roughly limit/2
  • Replay the boundary-burst scenario from pattern 01 — this limiter must deny
04

Token Bucket

Difficulty

Burst is a feature here, not an accident.

Key
rl:tb:{key}
Type
Hash — { tokens, last_refill_ms }
Config
Capacity int64, RefillPerSecond float64
-- lazy refill, inside the script
elapsed = now - last_refill
tokens  = min(capacity, tokens + elapsed/1000 * refillPerSec)

if tokens >= n then tokens = tokens - n            -- allow
else retry_after = (n - tokens) / refillPerSec   -- deny
end

HSET tokens, last_refill = now
PEXPIRE key (capacity / refillPerSec)             -- time to refill from empty

Gotchas

  1. Redis truncates Lua floats on return. 3.7 arrives in Go as 3. With fractional tokens that is a silent miscount. Return tostring(tokens) and parse with strconv.ParseFloat, or scale by 1e6 and return an integer. The defining gotcha of this pattern.
  2. A missing key means a full bucket, not an empty one. Letting nil collapse to 0 denies the very first request a user ever makes.
  3. TTL doubles as a memory strategy. capacity / refillPerSec is exactly how long an empty bucket takes to fill. A key idle longer than that is indistinguishable from a deleted one, so let it expire.
  4. No background refill goroutine. Lazy refill on read is O(1) and needs no worker. If you catch yourself reaching for a time.Ticker to pump tokens, stop.

Tests

  • Burst: capacity=10, rate=1/s → ten back-to-back requests allowed, eleventh denied
  • Refill: advance five seconds → exactly five more allowed
  • Ceiling: advance an hour → still only capacity requests allowed
  • Fractional tokens. rate=0.5/s, advance one second → half a token, n=1 must deny; advance another second → allowed. This is the test that catches gotcha 1.
  • RetryAfter equals (n - tokens) / rate
05

Leaky Bucket

Difficulty

Two variants in one package — the pattern with the most to teach.

(a) leakybucket.Meter — Redis, consistent with the other four

Type
Hash — { level, last_leak_ms }
Script
level = max(0, level - elapsed/1000 * leakPerSec); deny when level + n > capacity, otherwise level += n

Mathematically this is the dual of the token bucket — it counts water going in rather than tokens left over. Once both are written, the README should explain how they differ in meaning despite the symmetry in their formulas.

(b) leakybucket.Queue — pure Go, in-process

This is the original leaky bucket: requests queue and a worker drains them at a steady rate.

type Queue struct { ... }

func (q *Queue) Wait(ctx context.Context) error  // blocks for its turn, or ctx.Done()
func (q *Queue) Close() error                    // drain, stop the worker

A buffered chan struct{} is the queue, a time.Ticker is the spout. A full queue returns ErrQueueFull immediately rather than blocking indefinitely.

Gotchas — this variant exists for these

  1. Wait must select on ctx.Done(). Otherwise a cancelled request keeps holding its slot in the queue.
  2. Close() must drain the queue and stop the ticker or goroutines leak. Non-negotiable: run go test -race and add go.uber.org/goleak.
  3. Never close the channel from the sending side.

Tests

  • Meter: mirrors the token bucket tests with the direction reversed
  • Queue smoothing. Twenty requests into a queue at rate=10/s → total time around two seconds and evenly spaced, not bunched
  • Queue: cancel a context mid-wait → Wait returns ctx.Err() promptly with no leaked goroutine
  • Queue: Close() while requests are waiting → no panic, no leak (goleak in TestMain)

Optional extension: GCRA

The Generic Cell Rate Algorithm expresses a token bucket as a single “theoretical arrival time” value — one field per key instead of a two-field hash, genuinely O(1) in memory. It is what redis-cell and throttled implement, and it is the strong answer when an interviewer asks whether token buckets are memory-hungry.

HTTP API

GET    /api/limiters                        // all five patterns + current config
GET    /api/limiters/{pattern}/config
PUT    /api/limiters/{pattern}/config       // change limit/window/capacity at runtime
POST   /api/limiters/{pattern}/check        // the protected endpoint: 200 or 429
GET    /api/limiters/{pattern}/state?key=   // internal snapshot for the UI
POST   /api/limiters/{pattern}/reset?key=

Response headers

Use the names from the IETF ratelimit-headers draft. The modern spec drops the X- prefix, so no invented X-RateLimit-*.

HeaderWhenValue
RateLimit-Limitalwaysthe limit in force
RateLimit-Remainingalwaysquota left
RateLimit-Resetalwaysseconds until reset
Retry-After429 onlyseconds

Middleware signature, idiomatic Go, no framework:

func RateLimit(l limiter.Limiter, cfg Config) func(http.Handler) http.Handler
Note. This repository uses conventional REST, not the RPC-style endpoint rules from the Kotlin/Micronaut ruleset — those are tied to that stack and do not apply to a Go learning project.

Frontend

Vite + React + TypeScript, recharts for the timeline. No state library — useState covers everything here.

  1. Tab bar — the five patterns plus a sixth tab, Compare.
  2. Control panel — per-pattern config form (limit and window, or capacity and rate), Apply posts to PUT /config.
  3. Traffic generator — three modes: Single (one request), Burst N (N concurrent via Promise.all), Sustained (X requests per second for Y seconds).
  4. Timeline chart — time on the x-axis, one dot per request: green for 200, red for 429. This is what makes the difference between the algorithms visible rather than theoretical.
  5. State panel — polls /state every 250ms: tokens remaining, water level, sorted set size, or the two counters, depending on the pattern.
  6. Compare tab — fire the same traffic pattern at all five limiters and stack the five timelines on a shared time axis. Fixed Window's boundary burst and Token Bucket's burst allowance jump straight off the screen.
Deliberately skipped: SSE streaming, auth, dark mode, responsive polish. Add SSE when you want to watch traffic generated by k6 or hey rather than by the browser.

Testing strategy

LayerToolingRuns
Unitminiredis — an in-process Redis fake with EVAL support, plus SetTime() and FastForward() to drive the clockmake test, no Docker
Integrationtestcontainers-go against real redis:7-alpine, behind //go:build integrationmake test-integration
Racego test -race ./...CI and pre-commit
Goroutine leaksgo.uber.org/goleak in the leakybucket package's TestMainwith unit tests
Benchmarkgo test -bench=. -benchmem — latency and allocations per AllowNmake bench
Loadhey -n 10000 -c 100 or k6manual
Keep both layers. miniredis runs Lua through a Go interpreter, not Redis's own — float formatting, TIME resolution and reply types will diverge at the edges. Unit tests give a fast loop; integration tests prove the scripts behave on real Redis.

Write tests table-driven, the standard Go idiom:

tests := []struct {
    name  string
    steps []step   // { advanceMs, n, wantAllowed }
}{ ... }
